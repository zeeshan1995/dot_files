# Personal Copilot setup

This directory exports maintained user-level configuration, not the entire
Copilot home:

| Path | Purpose |
| --- | --- |
| `copilot-instructions.md` | Personal routing, engineering constraints, and permission boundaries |
| `agents/autonomy-*.agent.md` | Seven bounded planning, review, implementation, test, verification, and guardian roles |
| `skills/autonomous-delivery/` | Execution protocol, engineering/context references, blank templates, validator, and tests |
| `skills/autonomous-resume/` | Recovery without duplicate ownership or lost evidence |
| `skills/adversarial-review/` | Independent proposer/challenger review and good-enough acceptance |
| `skills/build-and-test/` | Evidence-based verification for ordinary changes and autonomous runs |
| `agents/impeccable-*.agent.md` | Optional Impeccable finish reviewer and documenter profiles |
| `licenses/impeccable/` | Upstream license and notices for those two profiles |
| `hooks/` | Existing Linux tmux restoration integration, separate from this setup |

The personal files retain their installed content except for synthetic test
fixture run/session labels and an associated example timestamp, generalized to
avoid publishing private runtime identifiers. No validator logic, assertions,
policy, or permission grants were changed. The dated `references/sources.md`
records historical choices; the current [protocol](skills/autonomous-delivery/references/protocol.md)
explicitly supersedes its former repair/review count bounds.

## Install or update explicitly

Prerequisites: Copilot CLI with personal instructions, skills, and custom-agent
support; Python 3.9+ and Git for the validator/tests. Sign in through Copilot
separately. These files do not contain credentials or install the CLI.

Run from this repository's root as your normal user. First inspect the intended
destination (`COPILOT_HOME`, or `~/.copilot`) and any existing `agents/`, `skills/`,
and selected files/directories. Do not copy through symlinks: resolve their
ownership and choose a regular-directory destination first. Review differences
and back up conflicts outside the repository before updating; existing personal
instructions should be merged deliberately rather than blindly replaced.

```sh
copilot_home="${COPILOT_HOME:-$HOME/.copilot}"
mkdir -p "$copilot_home/agents" "$copilot_home/skills"
cp -i .copilot/copilot-instructions.md "$copilot_home/"
cp -i .copilot/agents/autonomy-*.agent.md "$copilot_home/agents/"
for skill in autonomous-delivery autonomous-resume adversarial-review build-and-test; do
    mkdir -p "$copilot_home/skills/$skill"
    cp -i ".copilot/skills/$skill/SKILL.md" "$copilot_home/skills/$skill/"
done
for directory in references templates scripts; do
    mkdir -p "$copilot_home/skills/autonomous-delivery/$directory"
done
cp -i .copilot/skills/autonomous-delivery/references/*.md \
    "$copilot_home/skills/autonomous-delivery/references/"
cp -i .copilot/skills/autonomous-delivery/templates/*.json \
    "$copilot_home/skills/autonomous-delivery/templates/"
cp -i .copilot/skills/autonomous-delivery/scripts/*.py \
    "$copilot_home/skills/autonomous-delivery/scripts/"
```

`cp -i` asks before replacing an existing file. Answer **no** to retain it, then
merge the reviewed changes separately. Updates are file-by-file, not atomic;
finish reviewing the whole set before using it. No command deletes extra files
or copies hooks, sessions, settings, authentication, or caches generated by tests.
Neither
`setup.sh` nor `mac/setup.sh` runs these commands.

The two Impeccable profiles are optional. They require the matching upstream
**Impeccable 4.1.0** skill and its references, installed separately through
[Impeccable's supported setup](https://github.com/pbakaus/impeccable).
The caller supplies `reference/document.md` for the documenter, and
`reference/craft-floor.md`, quality-bar cards, captures, and applicable platform
references for the reviewer. The plugin tree and those dependencies are not
vendored here; the profiles alone are not a complete Impeccable installation.

After installing that dependency, copy the optional profiles and retain their
license/notices:

```sh
mkdir -p "$copilot_home/licenses/impeccable"
cp -i .copilot/agents/impeccable-*.agent.md "$copilot_home/agents/"
cp -i .copilot/licenses/impeccable/LICENSE \
    .copilot/licenses/impeccable/NOTICE.md "$copilot_home/licenses/impeccable/"
cp -i .copilot/THIRD_PARTY_NOTICES.md "$copilot_home/"
```

Restart or resume Copilot to refresh configuration. Confirm that the host
discovers the four skills and intended custom-agent names. Tool names,
independent contexts, authorized worktrees, messaging, and native scheduling
depend on the actual host. A profile's frontmatter is not proof that its tools
are callable or that its limits are enforced. Missing required capabilities
remain blockers; do not silently substitute other roles.

## Use and limits

An explicit autonomous coding request uses five planning gates: brainstorm,
requirements, architecture, design, and implementation planning. Independent
proposer/challenger reports and rebuttals precede acceptance; implementation
milestones and final independent verification also require review. Ordinary
edits use build-and-test without launching that lifecycle. Questions and setup
maintenance do not start autonomous workers or schedules.

Good-enough acceptance is anchored to approved scope and current-stage evidence:
resolve or refute real blockers, disposition advisories, and advance rather than
inventing polish work. Deterministic repair and review continuation have no
arbitrary count cap, but require distinct evidence-backed progress and preserved
history. Transient retry limits, permissions, user stops, budgets, and deadlines
still apply. At most four specialists execute concurrently, including the
guardian while running, subject to any lower actual limit.

The guardian is a bounded, read-only observer, not a supervisor. Five-minute
monitoring requires an authorized native schedule, actual registration receipts,
and saved configuration readback for the current run. Installing this directory
creates **no timer, hook, active worker, or running guardian**. It neither exports
nor changes an existing schedule. Missing automation is a recorded capability
gap with truthful event-only coverage, never a claim of continuous monitoring.

Templates contain empty/example state and cannot authorize a run. Keep actual
checkpoints, reports, logs, schedule receipts, and source snapshots in private
session artifacts outside the repository. The instructions-invoked validator
checks recorded consistency; it cannot authenticate reports, enforce billing or
permissions, keep a machine awake, or guarantee completion.

## Validate

From the repository root:

```sh
python3 -m unittest discover -s .copilot/skills/autonomous-delivery/scripts -p 'test_*.py' -v
```

The tests exercise synthetic positive and negative checkpoints, real validator
CLI exit codes, source identity, and cross-file guidance contracts. They do not
launch agents, install configuration, or prove live autonomous delivery. See the
root README for existing dotfiles checks.

For an actual authorized run, pass the appropriate private checkpoint path:

```text
python3 <copilot-home>/skills/autonomous-delivery/scripts/validate_checkpoint.py audit <run-directory>/checkpoint.json
python3 <copilot-home>/skills/autonomous-delivery/scripts/validate_checkpoint.py implement <run-directory>/checkpoint.json
python3 <copilot-home>/skills/autonomous-delivery/scripts/validate_checkpoint.py complete <run-directory>/checkpoint.json
python3 <copilot-home>/skills/autonomous-delivery/scripts/validate_checkpoint.py snapshot <absolute-worktree-path>
```

Do not test completion against a live run merely to install this setup. Empty
templates are expected to fail validation.

## Keep exports private by default

Future updates should copy only the maintained paths listed above and review the
diff before publishing. Never bulk-copy a Copilot home. Exclude credentials,
account/config secrets, authentication caches, sessions, chats, attachments,
checkpoints, reports, logs, databases, caches, downloaded plugins, unrelated
settings, private URLs, machine-specific paths, and workplace content. Keep any
export-comparison evidence local rather than committing a runtime inventory.
